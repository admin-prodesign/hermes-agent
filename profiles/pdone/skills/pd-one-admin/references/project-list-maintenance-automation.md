# Project List maintenance automation

Use this reference when planning, implementing, or reviewing PD One automations for the Google Sheet `良器-跨部門-專案追蹤表 Project List` (`1QAdHzC5jaFDrs-xqDUY8Pnzq-_gz_dU7hNUyqpYJtLA`).

## Current source facts

- Company wiki source page: `/home/prodesign/.hermes/company-wiki/main/sources/google-sheets-project-list.md`.
- Main tab: `專案追蹤`.
- Key columns:
  - F `處理人` — responsible person / people.
  - G `改善歷程` — human-readable history/progress log; append, do not replace.
  - I `對話連結` — Mattermost conversation/thread link. This was renamed from older scanned header `關聯對象`; do not treat that old header as current.
- Add automation-only visible identifiers at the far right, not before F/G/I, so existing human workflows and formulas are not shifted.

## Recommended architecture

Split responsibilities:

1. **Bound Google Apps Script for row identity**
   - Add/use a far-right column `PD One Issue ID`.
   - Assign IDs like `PL-2026-0001` when a row becomes meaningfully populated.
   - Use `LockService` + `PropertiesService` counter.
   - Do not overwrite existing IDs.
   - Run both manual/backfill and time-driven trigger; `onEdit` alone can miss formula/import/paste cases.

2. **PD One/OpenClaw backend for Mattermost and DMs**
   - Read rows by `PD One Issue ID`, never by row number alone.
   - Monitor Mattermost thread links in column I `對話連結`.
   - Store processed Mattermost post IDs/timestamps locally and mark them processed only after a successful sheet write + readback.
   - Append concise dated progress notes to column G `改善歷程`.
   - Run Thursday follow-ups only on Taiwan workdays.
   - DM each responsible person one item at a time. After their reply is written/read back, send the next item. Use timeout/reminder logic so one unanswered item does not block all remaining items.

## Supervisor-agent / third-party loop

When Andy says he is babysitting the Thursday Project Tracker automation too much, do not propose only more reminders. Treat it as a need for an independent oversight loop that knows the intended outcome and audits PD One execution.

Recommended pattern:

1. Keep the existing worker timers focused on doing work: weekly owner DMs, reply polling, Sheet appends, and thread monitoring.
2. Add a separate supervisor/checker job with no send/write permissions by default. It reads logs, state, Mattermost prompt receipts, and Sheet readbacks, then reports only exceptions.
3. The supervisor should compare intent against evidence, not just process health: expected Thursday prompts, one active prompt per owner, pending queue continuity, matched replies after prompt timestamps, Sheet column-G readback by `PD One Issue ID`, reminders due by Taiwan workday slot, and stale/error logs.
4. Use quiet watchdog semantics: no news when all invariants pass; concise admin alert when an invariant fails, including the missing receipt, affected owner/issue id, and a safe recovery recommendation.
5. If recovery requires employee DMs, Sheet writes, policy changes, gateway restart, or broad log/history search, the supervisor must stop at a dry-run/recommendation unless Andy has explicitly approved that action class.
6. Prefer an existing class-level reliability mechanism (Hermes cron/watchdog, systemd timer, or review-log row) over a bespoke conversational agent. If a true separate agent is needed, give it a narrow self-contained prompt, read-only tool surface, and links to this reference plus `automation-reliability`.

For Chinese names, search both the full name and the given-name substring because Mattermost may index `first_name=given` and `last_name=surname` separately. Only auto-enable exact display-name matches; otherwise leave mappings disabled/unresolved for review.

- For DM follow-up smoke tests, send a real Mattermost DM to the requester/admin, read it back by post ID, ask them to reply, then poll the DM channel. Capture both threaded replies (`root_id` equals prompt post ID) and plain DM replies in the same channel after the prompt timestamp. Keep the smoke test non-mutating by using synthetic state and `poll-dm-replies` without `--write`; only turn on `--write` after verifying the matched reply and duplicate/row-ID guards.
- The reply poller should store pending prompts in state with `mattermost_user_id`, `channel_id`, `post_id`, `sent_at`, `issue_id`, and status. On live `--write`, append via `PD One Issue ID`, verify readback, then mark the prompt completed in state and record `reply_post_id`; do not mark processed before the Sheet write succeeds.
- If a Project List follow-up reply is first discovered through `review_log` as a `dm_no_reply_evidence` row, treat it as a recoverable reply-poller miss rather than a generic chat outage. Fetch nearby Mattermost DM posts, locate the preceding `專案追蹤更新 / Project List update` prompt, extract the stable `PL-2026-####` id, append the user reply to column G by `PD One Issue ID`, verify readback, then close the `review_log` row with both the prompt post id and reply post id.
- For health checks, do not stop at `systemctl --user status` or green timer exits. Verify end-to-end state consistency: inspect the weekly send log for actual `post_id` receipts, read `state/project-list-maintenance/state.json` for `pending_dm_prompts`, fetch the prompt post/thread/channel in Mattermost, and compare any owner replies after the prompt timestamp against the Sheet history readback for the matching `PD One Issue ID`. A healthy reply poller should not report `checked_prompts: 0` immediately after live weekly sends unless all prompts were completed and their replies are already present in column G.
- If a live Mattermost DM prompt exists but `pending_dm_prompts` is empty, treat it as a reply-poller/state-loss incident. Use the prompt post id from `followup-send.jsonl` to fetch same-channel posts after the prompt timestamp; accept both threaded replies (`root_id` equals prompt post id) and plain DM replies in that channel by the mapped owner. Backfill only after explicit approval, appending by stable issue id and verifying Sheet readback.
- For owner discovery, do not rely only on a manually maintained Google Sheets name → Mattermost map. Use a layered resolution path: split the Sheet `處理人` names, resolve each name against AppSheet employee data first (prefer `HR_E_A_S` if available, but fall back to `HR_Employees` when the settings table/API response is unavailable), then search Mattermost using full Chinese name, given-name substring, AppSheet romanized name tokens, AppSheet email/localpart, and employee ID. Only auto-enable high-confidence Mattermost matches such as exact display-name or email-equivalent matches. Persist low-confidence candidates as disabled/unresolved evidence and surface them to Andy/admin instead of silently skipping or guessing. The weekly sender should run this best-effort discovery before building its send queue; unresolved/disabled mapping gaps must federate to PD Neo/admin as `pd-one.capability_gap` with candidate-search evidence, not a narrow custom event type.
- When fixing reply-poller state loss, check for concurrent timer writes: the thread monitor and weekly sender may save the same JSON state file near the same minute. State writes must merge dict-valued buckets such as `pending_dm_prompts`, `last_seen_thread_posts`, and `weekly_runs` rather than replacing the whole file from a stale in-memory snapshot. Add regression coverage that a monitor save cannot erase a newly sent waiting prompt.
- Add a loud health alert for `poll-dm-replies --write` runs that report `checked_prompts: 0` within the week after a live `followup-send.jsonl` entry with actual sent prompts. This is not a healthy idle state unless every sent prompt was completed and Sheet history already contains the replies.
- If `pending_dm_prompts` was lost after weekly sends, the reply poller should recover recent prompt records from `followup-send.jsonl`, reconstruct the DM channel, and rebuild `remaining_issue_ids_for_person` from the current Sheet queue so a completed reply continues to the next assigned issue instead of restarting or stopping at the first item. Guard this path against duplicate prompts by checking for an active waiting prompt per user before sending the next item.
- Plain, non-threaded Mattermost DM replies are allowed for non-technical users, but they must be filtered so unrelated same-channel requests/questions are not appended as Project List updates. Prefer threaded replies; for plain DMs, accept progress-like text (`已開單`, dates, `沒有更新`, progress keywords) and reject new question/request patterns such as `請提供...？`.
- Employee replies to PD One `Project List update / 專案追蹤更新` prompts are collector acknowledgements, including unthreaded top-level DMs and short action-verb status text. Classify them `ok` with `quality_review_excluded` before `no_reply_evidence`, and skip them in the employee-reply quality supervisor. A silent Sheet write or a next-item prompt posted as a new DM is not a missed employee answer. Do not page Andy for missing write receipts on those acknowledgements; verify writes through the reply poller health path instead. Keep genuine questions in the same thread in normal quality review.
- When the conversational turn receives that acknowledgement, do not treat the action verb as a request to schedule mold repair, create a case, or append column G again. The reply poller owns the append and may already have completed the prompt and sent the next item before this turn answers. Look up `pending_dm_prompts` by the key `{YYYY-MM-DD}:{mattermost_user_id}:{issue_id}` first. The date is the prompt send date, not today; if it is unknown, match the thread root to that record's `post_id` and use the key you find. Completed records stay in that dict. Do not scan the user id alone; historical prompts flood the search. A record can stay `waiting_reply` after `superseded_reason` `new_recurring_followup`. The poller still matches a threaded reply whose `root_id` equals that prompt `post_id`, appends column G, and enqueues the next id from that record's remaining list. Do not treat the superseded flag as a miss, and do not send a second next-item DM from the current Thursday cycle. If `status` is `completed` and `history_append_result.readback_verified` is true, confirm the cell tail with typed Sheets get (`include_values`) on `target_range`, then send a short receipt: issue id, progress text, and verified range. If `status` is `completed` but `history_append_result.skipped` is `source_comment_already_present`, do not wait for `readback_verified`; the poller will not rewrite that prompt. Use the dated-line recovery below before the receipt. Name the next issue only when a waiting prompt has `continued_from_prompt_id` pointing at the completed prompt, so the owner does not treat the new DM as a repeat. If `status` is still `waiting_reply`, do not call terminal or `execute_code` to sleep or to run `poll-dm-replies --write`. An employee Mattermost turn posts an approval card into the origin thread before that command starts, and a chat-turn `--write` can also send the next owner DM. The reply-poller timer fires about every 5 minutes. Re-read the same prompt key after the next tick only when the latest `reply-poller.jsonl` entry is a successful poll. The poller reads the full sheet inside `recover_missing_prompts_from_send_log` before it matches replies, so a sheet-read failure at the log tail leaves the prompt `waiting_reply` on every tick. A typed Sheets get that fails the same way is that outage, not a cue to use terminal. Do not append column G from the chat turn while status is still `waiting_reply`. Tell the owner the reply was received, the history line is not written yet, and they must not send the same text again: a second post becomes a second history line after the writer recovers. Do not open a ticket or a second workflow. Send the verified receipt only after `status` is `completed`, `readback_verified` is true, and the typed Sheets cell tail contains that dated source line. A chat-turn append duplicates history when that dated source line is already in the cell. A threaded reply whose `root_id` equals the prompt `post_id` matches without the plain-DM keyword filter, so a short status in that thread is a normal match, not a miss. Employee sessions must use the typed Sheets read, not terminal.

- Thursday follow-up DMs start at the weekly timer (`pd-one-project-list-weekly-followup.timer`, Thursdays 01:00 UTC / 09:00 Taiwan). Each Thursday **resets the cycle**: unanswered waiting prompts from before that Thursday are superseded and a fresh one-item ping is sent per mapped/enabled owner (remaining issue IDs stashed). Skip only a waiting prompt already sent **this Thursday** (`already_waiting_reply_this_thursday`) or an issue already replied since last Thursday (`already_replied_in_thursday_cycle`). - Reply-poller nudges should be threaded @mention reminders, not new standalone DMs. Before sending any reminder, re-read the current Sheet row and responsible-person map; if the active prompt's `處理人` no longer maps to that Mattermost user, mark the old prompt superseded/`responsible_changed` and do not remind the old owner. The durable behavior is two idempotent Taiwan-workday slots per waiting prompt: AM after 09:00 TPE and PM after 14:00 TPE, through the Monday deadline. Store reminder state by prompt/date/slot so the 5-minute poller cannot spam beyond one AM and one PM nudge. For smoke tests, use `poll-dm-replies --reminder-slot am` and `--reminder-slot pm` dry-runs; the PM dry-run should show `would_send` when an AM reminder already exists and the prompt is still waiting.
- When continuing an owner's multi-item queue after a reply, treat stored `remaining_issue_ids_for_person` as a snapshot hint only. Re-read the Sheet and filter the remaining IDs against the current `處理人` mapping before sending the next prompt, so reassigned items are not carried forward to the previous owner.
- Project List health checks must verify both monitored conversation ingestion and owner-prompt behavior. A good smoke bundle includes: Sheet header/row/link counts (`rows`, active follow-up rows, rows with Mattermost links, total linked post roots), `monitor-threads` dry-run `checked_threads`/`issues_with_new_posts`, `poll-dm-replies` dry-run `checked_prompts`/`matched_replies`/`reminders`, systemd timer/service status with next run times, and unit tests. Write one value-range JSON array under the profile `cache/scratch` or another approved PD One tmp/artifacts/cache root. Dry-run `pd_one_sheets_batch_update` with `input_mode=RAW`. Abort unless the payload prefix equals the live cell and only the new dated tail differs. Live write uses `confirm_live_write='RUN LIVE SHEETS BATCH UPDATE'` plus that readback range. This workflow write uses the PD One Sheets account when the tool has no requester id; do not open a PDAPP ticket for it. Confirm with a separate get: the cell must still start with the old history and end with today's dated source line. - When auditing whether owner DMs started and continued, use the send log plus reply-poller log as the source of truth: convert timestamps to Asia/Taipei, list `sent`/`skipped` from `followup-send.jsonl`, then summarize each `matched_replies[]` chain event (`from_issue`, `reply_post_id`, `next_issue_ids`, `next_prompt.issue_id`, `next_prompt.post_id`, `next_prompt.skipped`). Repair from the reply-poller log with a backup of `state.json`, add load-time normalization/regression coverage, and verify the post-repair waiting queue contains only genuinely pending prompts.
- Keep production recovery logic out of isolated tests and synthetic state paths. Verification receipts should include the dry-run result, next systemd service status, latest JSONL entry, and relevant unit test coverage.
