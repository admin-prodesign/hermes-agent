# AppSheet sync Performance Analyzer triage

Use when users report slow app syncs and ask whether a helper/queue table such as `ProcessingQueue` is the cause.

## Workflow

1. Pull fresh AppSheet Performance Analyzer data from the authenticated `/manage/exportlog` endpoint for the requested window. For 24h windows, chunk sync-only exports by hour to avoid endpoint caps/truncation.
2. Run a separate failures-only export over the same window, and a recent all-operations sample (for example last 6h in 30m chunks) if you need queue/process volume context.
3. For user-visible sync slowness, filter to sync rows only (`syncs=True`, adds/updates/deletes/workflows/reports/API/documents disabled). Keep rows with `Result` or `Properties.Performance`; exportlog often emits paired summary/detail rows with the same timestamp.
4. Parse `Properties.Performance` JSON instead of relying only on top-level tables/process counts:
   - generated `perf-scan-*.json` reports are usually shaped as `{ "meta": ..., "report": ... }`; do not expect `rows`, `failure_count`, or rankings at the top level
   - in raw rows, `Properties` may be a dict, a JSON string, or a Python-literal-looking string with single quotes; parse JSON first, then fall back to `ast.literal_eval()` before reading `Properties.Performance` or failure `Exception` fields
   - `Properties.Performance` is often a JSON **string** even when `Properties` itself is already parsed; `json.loads()` that string before traversing it
   - AppSheet timing values are often strings like `00:00:58.4537074`; parse `[[days.]HH:]MM:SS.fraction` into seconds before computing p50/p90/max
   - total sync duration: root `Performance.Time`, `PerformanceTimingRoot.Timer.Time`, or root `Timer.Time`
   - per-table root loads: timing nodes with `Mid == 116`; table name is param `Pid 13`
   - virtual/computed columns: timing nodes with `Mid == 222`; table is param `Pid 13`, column is param `Pid 1`
   - params may be nested as `Params.ParamList` entries (`{"Pid": 13, "Value": "Case"}`), not a flat map
   - row/column counts usually appear in descendant params `Pid 9` / `Pid 3`
   - pushed source predicates usually appear in descendant params `Pid 18`; capture these when judging whether a security filter became SQL/provider-pushed
   - exportlog commonly emits paired rows per sync timestamp; treat rows with `Properties.Performance` as the detailed timing sample count and ignore the paired summary-only rows for duration stats
   - if the generated scan report only lists counts/top failures and omits timing rankings, inspect the companion `perf-raw-*.json` rows directly; compute duration/table/VC stats from each row's `Properties.Performance` rather than assuming the scan had no timing evidence
   - when writing an ad hoc parser, traverse through the root `PerformanceTimingRoot` object as well as nested `Children`; otherwise table (`Mid == 116`) and VC (`Mid == 222`) timings can be missed even though total durations parse correctly. Prefer known timing roots/children first and avoid recursively walking the entire raw/performance object on large exports unless necessary, because repeated metadata/API-ready blocks can make the parser hang or time out.
   - raw report extraction needs explicit branching: `rows = raw` only when the top-level JSON is a list; if it is a dict, use `raw.get("rows")` / `raw.get("Rows")`. Avoid compact ternary/operator-precedence forms that can accidentally return `[]` for dict-shaped raw files.
   - timestamps in raw rows may be `EventTimeStamp` rather than `TimeStamp`/`timestamp`; use that key for failure examples and window correlation.
   - for failures-only raw rows, prefer nested `Properties.Exception` / `Properties.Errors` over the top-level `Result` when classifying exceptions; otherwise direct `Add row` failures can be mislabeled as generic `Failure` / `other_failure` even when `Properties.Exception` contains the ASDB row-not-found or duplicate-request signature. Also include `Properties["Process Name"]` when separating direct no-process rows from bot/process failures.
   - reusable parser: `scripts/perf_raw_timing_analysis.py <perf-raw.json> [perf-scan.json] [out.json]` handles the common raw/exportlog shapes above and writes a compact analysis JSON with sync duration stats, table p90 rankings, virtual-column p90 rankings, failure classes, and examples. Use it when a steward/report needs grounded rankings but the generated `perf-scan-*.json` only lists counts/top failures. If that helper is not present in the active profile checkout, keep the run moving by writing a one-off parser under the steward log directory, saving its output beside the scan artifacts, and including that analysis path in the remediation plan.
   - scan stdout can become huge/truncated when `TOP_FAILURE_MESSAGES` includes full stack traces. Treat the printed `REPORT:`, `RAW:`, and `PROMPT_PACKET:` paths as receipts, then inspect the saved JSON and parser output instead of relying on terminal stdout for rankings or failure classes.
   - `perf_analyzer_scan.py` filenames are derived from the scan end timestamp. If you rerun table-specific or failures-only follow-up scans with the same explicit `--end` as a gate packet, write them under a separate `--out-dir` subdirectory; otherwise the follow-up scan can overwrite the gate `perf-scan/perf-raw/perf-prompt-packet` files.
   - Do not compute AppSheet add/edit success rates from a single non-failures-only table-scoped export without checking a matching failures-only export. In live runs, table-scoped non-failures-only exports have omitted failures that appeared in failures-only exports over the same requested window; use all-operation exports as success/context evidence and combine with failures-only scans for failure counts, with denominator caveats when endpoint caps/filtering are present.
5. Rank by avg/p50/p90/max seconds for both root table loads and virtual/computed columns. Use p90 for the operational headline; max alone can be noisy.
6. For before/after AppSheet definition changes, split the export exactly at the stable-promotion/implementation timestamp and compare both:
   - a broad pre-window (for baseline), and
   - a same-duration immediate pre-window vs immediate post-window (for fairer traffic/time-of-day comparison).
   Always report the sample sizes; if the post window only has a few detailed sync rows, call the result directional rather than conclusive.
   - For automation/Heartbeat/write-path performance, run both `--failures-only` and non-failures-only exports. Failures-only scans show failure volume but hide total operation volume; the all-rows scan is needed for success/throughput context and for proving that a process improved rather than merely ran less often. Broad non-failures exports can hit the AppSheet 1000-row cap even over a 2-hour window, so chunk all-operation scans into smaller windows (for example 15 minutes) and record whether any chunk still returns exactly 1000 rows before using denominators. Keep the failures-only export as the authoritative failure count when all-operation and failure-only counts disagree.
   - Add/update all-result exports commonly include paired `RecordType=Start` rows with blank `Result` before the final `Success`/`Failure` row for the same save attempt. When computing save success rates, count completed final rows (`Result=Success` plus failures from the matching failures-only export), keep blank-start rows as attempt/context evidence only, and note this caveat in denominator artifacts.
   - For steward add/edit denominator traces, chunk all-result exports by target table and include both `Add row` and `Update row`, but classify direct user save reliability from failures-only rows with an empty process name; keep same-table bot/process rows (for example notification, thumbnail, cache, or hourly maintenance failures) in a separate automation bucket so they do not pollute the direct add/edit denominator.
   - For retry-heavy upload failures such as `A duplicate request is already in progress`, also group completed stop rows by a sanitized request/client/user key and report request-bucket outcomes (`success_only`, `mixed_success_and_failure`, `failure_only`) alongside row-level success rate. Repeated `Failure` stop rows can make row-level success look worse than unique request outcomes, while mixed buckets prove retry turbulence that is distinct from a deterministic schema/formula failure.
  - When building redacted add/edit artifacts from `perf_analyzer_scan.py`, do not persist scanner stdout/stderr tails into the redacted JSON/brief: compact stdout can include `updatedKeys`/row keys, and duplicate-request exception heads can include raw Client ID / Request ID. Store only counts, local raw-file paths, and salted hashes; scrub exception heads before validation and run a search for raw ID/key patterns before using the artifact in an approval/support packet.
   - When rolling watchdog windows overlap the deployment time, create explicit ad hoc windows that do not cross the stable-promotion boundary before making the headline claim.
   - If a targeted HeartBeat process improves but failures remain, classify remaining failures by `Process Name` and say which process class is still noisy rather than calling the whole HeartBeat system fixed.
7. Separately classify failures by signature (TaskCanceledException/cache lock, Spanner OperationCanceledException, table not accessible, sheet grid limit, schema mismatch). Do not mix these with sync-duration bottlenecks unless they appear in sync rows.
8. Answer the specific hypothesis directly: compare the suspected table's sync timing and row count against the slowest tables/columns.

## Interpretation pattern

- A large `ProcessingQueue` can create automation/append pressure and grid-limit failures, but it is not necessarily the sync bottleneck. If its p90 sync table load is only a couple seconds while `Case_Updates`, `Case`, or `ActivityLog` p90s are tens of seconds, say so clearly.
- `ProcessingQueue` grid-limit errors (`Range (ProcessingQueue!...) exceeds grid limits`) are a separate reliability issue: they can break workers and make symptoms worse, but they do not by themselves prove slow app sync.
- `Case_Updates` + `Case[Related Case_Updates]` is a common high-impact sync pattern: the child table can be large, and the parent related-list virtual column can spend most of the sync budget scanning it. When `Case[Related Case_Updates]` p90 is high, recommend cached latest/summary fields or drill-down-on-open patterns instead of broad related-list virtuals during sync.
- A child security filter such as `IN([CaseID], Case[CaseID])` may show up in provider timing as a `CaseID InList ...` predicate, but that does not guarantee the actual child table row count dropped. Verify the descendant `Pid 9` row count before claiming a row-volume fix. If the row count remains high (for example all historical `Case_Updates`, or row counts around 17k-27k for `Case`/`Case_Updates`), say the visible parent set is still too large and recommend row-local cached predicates copied onto the child table, tighter parent visibility, or cached summary columns for a durable SQL-optimized fix.
- For `ActivityLog`/attachment sync slowness, check both parent rows and attachment tables. `ActivityLog_Attachments` can be a secondary bottleneck with large row-count spikes even when `ActivityLog` itself is timestamp-filtered; recommend parent-visible attachment filters or tighter timestamp/key-target rules.
- When `getAllTables=True` persists despite `Behavior.DeltaSync=true`, inspect `Behavior.IncrementalSync` and the relevant `AppData.DataSets[].UpdateModeExpression` before proposing local sync changes. In Pro-Design, top ASDB tables may delegate normal-user update/write capability to `HR_Employees_AppSheet_Settings[Appsheet Data Access Mode]`; first gather aggregate read-only settings distribution. Treat `UpdateModeExpression` / `Appsheet Data Access Mode` as update-permission context, not proof by itself that delta/full-load sync behavior is app-owned. If Analyzer shows pushed timestamp predicates for `ActivityLog`/attachments, do not describe their security filters as wholly unpushed; separate persistent full-load/getAllTables behavior from provider predicate pushdown.
  - For a support-ready read-only appendix, parse the sync raw rows into paired start vs detailed `Properties.Performance` samples, count `getAllTables` and `AppDefinitionChanged` on the detailed rows, compare current `Behavior.DeltaSync` / `Behavior.IncrementalSync` with pre-change snapshots, and add redacted row-count/predicate-kind context per `Mid == 116` table. If low/zero-row `google_tables` sources still spend tens of seconds while top virtual-column p90 is under ~1s, classify the headline as root table/source-read + full-load behavior rather than a single VC or simple row-volume issue. A future `IncrementalSync` canary remains a live sync-behavior gate; do not apply it before support/offline evidence and a separate approval packet.
- `ActivityLog` and `ActivityLog_Session_Items` can also dominate, especially label/related-row virtual columns that dereference parent data.
- Pro-Design `Lookup[RowCount_Realtime]` / `RowCount[Count_RealTime]` can become a top VC bottleneck because it counts multiple user-specific `Case_*` slices during sync. If it appears near the top, recommend replacing real-time COUNT VCs with cached/materialized counts or hiding/de-scoping the realtime count column from normal sync surfaces.
- `GoogleTranslate` sheet/schema column mismatches may show as many sync failures. Treat them as a separate sync-failure class even if the original complaint is “slow sync.”

## Report shape

Keep the final answer concise and operational:

- Window checked, with UTC and TPE if relevant.
- Fresh source: AppSheet `/manage/exportlog` Performance Analyzer endpoint.
- Sync count and duration stats: average, p50, p90, max.
- Top table bottlenecks and top virtual/computed column bottlenecks.
- Direct answer to the suspected cause, e.g. “not mainly ProcessingQueue,” with its row count and p90 timing.
- Separate failures discovered that are not the main sync-duration root cause.
- Evidence path if artifacts were written locally.
