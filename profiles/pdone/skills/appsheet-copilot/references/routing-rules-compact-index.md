# AppSheet Copilot — routing rules

## Routing Rules
- Natural-language user-facing record create/update flows for ActivityLog, child ActivityLog, Case, or Case_Updates: load `appsheet-record-ops` first, then use this skill for schema/API details as needed.
- Schema-sensitive advice: inspect/sync the deployed AppSheet definition first; do not invent table, column, action, bot, slice, or security-filter names.
- A Lookup table probe that returns 0 rows is not proof the value is absent. Read the Lookup sheet. The API user's security filter can hide rows the sheet still has.
- Editor definition save/promote (not row Data API): load `references/pd-one-appsheet-definition-mcp-call-path.md` — inspect → dry-run apply → live apply only with PDAPP grant `appsheet_definition_apply` and exact confirm phrase; Mattermost shared-room MCP is OK for admin without loosening sender/card gates.
- Monitoring whether staff are creating a newly required ActivityLog category: load `references/activitylog-adoption-monitor.md`. Do not treat a record count as compliance. Name a visible proxy event, state what that proxy cannot see, report gaps to the requester, and do not message staff unless asked.
- Making a column not required: `IsRequired=false` does not clear `TypeAuxData.Required_If`. Follow the Column requirement edits section in `references/appsheet-editor-api-saveapp-pitfalls.md`. After the stable readback, update any PD One digest that still treats a blank value of that column as incomplete. Do not change `Show_If` unless the requester asked to hide the field.
- Adding a physical column on a Google Sheet-backed AppSheet table, including `ActivityLog`: load `references/activitylog-google-sheet-column-add.md` before the first write. Confirm `ProviderName` first. Do not save until non-virtual schema order, excluding `_RowNumber`, equals the live sheet header order. A schema insert in a different position than the new header shifts later columns, so a view grouped by `Category` displays `Sub-Category` keys instead of Lookup translations. Also write the new name into both `ViewDefinition.ColumnOrder` and `Settings` JSON `ColumnOrder`, plus the slice `Columns` list, or the field stays hidden.
- Changing which columns one form shows, or forcing a `LINKTOFORM` field to open blank: follow Form column order and blank defaults in `references/appsheet-editor-api-saveapp-pitfalls.md`. Patch both column-order stores. An `InitialValue` that always returns blank is dropped on save. A short source description goes into the title only when it is not blank and shorter than the title max; pass an explicit blank for the long description in that case.
- Adding a filtered menu list like `Case_My`, or grouping a Ref `EnumList` by a related number: follow Menu views and group-by in `references/appsheet-editor-api-saveapp-pitfalls.md`. Do not set cloned `*Evaluatable` fields to null. Do not `GroupBy` the Ref list when the requester asked for a number column. The view stays hidden until the Lookup row exists and the user adds the view id to Navigation Bar or Menu Items.
- A new case type that must stay hidden until launch: do not add the type value to the type column `Valid_If`, keep new views `ShowIf` FALSE, and still write `ColumnOrder`. When cloning a catalog-to-child add-row action, do not copy a `MAXROW` parent-key assignment. Clone `ActionDefinition` from the same action type. Ref-action inputs use `InputName` / `InputValue`. Do not invent an `Inputs` entry the loaded definition does not already have, and do not promote while a formula still references that missing input. See `references/appsheet-editor-api-saveapp-pitfalls.md`.
- Digitizing mold repair orders onto shared Case: load `references/mold-repair-case-record-model.md`. Case is the order. In-house work, outside jobs, and trials are their own tables. Checklist marks are rows. Do not merge vendor write-off into the outside-service row. Mold Repair status rows are Lookup rows scoped to that type. Do not reuse another type's status keys.
- AppSheet-backed Google Sheets can fail sync from extra blank grid columns; for helper tabs like `GoogleTranslate`, compare physical sheet grid width to the AppSheet schema excluding `_RowNumber`, trim accidental blank columns, and avoid schema regeneration unless the field is intentional.
- Data pulls/exports: default to the Data Studio prototype app unless Andy explicitly asks for deployed-app data writes or links.
For AppSheet editor version mistakes, restore/revert attempts, or physical AppSheet Database cleanup after column-add errors, use `references/appsheet-version-lineage-and-db-cleanup.md`: Pro-Design major versions are `YY.MMDD00`, AppSheet restore creates a new latest version rather than rolling back version numbers, and physical DB headers must be checked separately from app-definition `DataSchemas[]`.
For offboarding/access cleanup questions like “who recently left and needs removal from AppSheet user list?”, use `references/appsheet-offboarding-access-audit.md`: query recent `HR_Employees[Employment Status] = "Not Employed"` + `Separation Date`, inspect AppSheet access-bearing fields, cross-check `HR_Employees_AppSheet_Settings` by `PersonID`, and answer as an audit/dry-run unless an approved bounded write is explicitly authorized.
For broad current-health questions like “How does AppSheet look now?” use `references/appsheet-current-health-check.md`: run fresh read-only failures-only and sync-only Performance Analyzer scans, parse sync raw timings, compare with the latest steward window, distinguish top-level sync durations from nested table/virtual-column timings, and answer with a concise operational verdict plus evidence paths. For `ActivityLog` as a recurring sync bottleneck or questions about splitting it by category, use `references/activitylog-performance-decomposition.md` before recommending schema changes. For the first 5S physical split / `5S` and `5S_Attachments` column design, use `references/activitylog-5s-physical-split.md`: audit actual `Category = "5S Action"` usage with bounded selectors, use `5S*` naming (not `FiveS*`), avoid cloning unused generic `ActivityLog` columns, split attachments when reducing photo/cache contention is a goal, and account for AppSheet Database editor quirks. For 5S visibility reports where users see other people's records, use `references/activitylog-5s-myteam-visibility-retarget.md`: verify whether the `ActivityLog_5S_MyTeam` view/control is wrongly pointed at broad `ActivityLog_5S_Slice`, patch only `Presentation.Controls[].TableOrFolderName` back to `ActivityLog_5S_MyTeam`, promote stable, sync definition, and smoke-test with run-as user counts. When physical AppSheet Database tables already exist but need to be added to the main app definition with refs, `Enum`/`EnumList` base `Ref`, key/label settings, and `Show_If`/`Editable_If`, use `references/appsheet-db-table-add-to-app-definition.md`; poll `/api/loadApp` after save timeouts because large `/api/saveapp` calls can commit after the tool/CDP call times out. For app-definition repairs after AppSheet Database table rename/schema regeneration, validation errors that only show in the editor, stale view table names, invalid XLSX templates, or source-qualifier/provider-metadata pitfalls, use `references/appsheet-api-schema-repair.md` and prefer API (`/api/loadApp` + `/api/saveapp`) over browser UI automation. When physical AppSheet Database tables have been renamed and schema regeneration broke app-level types/refs/templates, use `references/appsheet-db-table-rename-schema-regeneration.md`; repair via API first, avoid changing existing source metadata unless deliberately re-adding a source, and verify the specific editor errors are gone. For scheduled XLSX report rebuilds after a table rename, especially when the user asks to duplicate rather than replace an automation/template, use `references/appsheet-xlsx-template-source-binding.md`: keep the original untouched, create disabled duplicate automation objects first, bind the duplicate template separately, and treat `403 Insufficient permissions to add source` as a Drive-source authorization blocker. For questions about moving Google Sheets tables to AppSheet Database for performance, use `references/appsheet-database-migration-performance-assessment.md`: map `DataSets[].ProviderName` (`google` vs `google_tables`) to p90 timing rankings before recommending migrations, and separate helper/queue reliability wins from true sync bottlenecks. For slow AppSheet sync/performance complaints: use `references/sync-performance-analyzer-triage.md` to pull fresh `/manage/exportlog` sync-only data, parse `Properties.Performance`, rank table/virtual-column timings, and separate sync-duration bottlenecks from queue/grid-limit automation failures. For multi-version performance patch work with live-test/revert/wiki requirements, use `references/appsheet-performance-versioned-live-test-log.md` to enforce baseline → single-version patch → stable readback → clean post-promotion analyzer windows → company-wiki receipt update. For prototype/Data Studio apps whose purpose is full data reads/writes, also use `references/prototype-datastudio-performance-review.md` to separate definition correctness from human load-speed optimization and avoid recommending filters that would break complete reporting. If generated scan reports omit timing rankings, run the reusable parser `scripts/perf_raw_timing_analysis.py` against the companion `perf-raw-*.json` to produce duration/table/virtual-column rankings and failure classes. For proactive AppSheet runtime monitoring, app-not-runnable detection, watchdog/steward jobs, or approval-gated remediation planning, use `references/appsheet-performance-steward-watchdog.md`. When failures are dominated by noncritical thumbnail/media lanes such as `Process for HeartBeat - PQ - Thumbnail` or `Process for HeartBeat - PQ - Thumbnail Push`, use `references/thumbnail-lane-pressure-pause.md` before proposing a pause or worker-event disable. For `Case`/`Case_Updates` slowness caused by `[Related Case_Updates]` or parent-child VC cost, also use `references/case-updates-cache-performance.md`; for the 2026-06-11 analyzer-backed proposal to replace `Case[Related Case_Updates] = REF_ROWS("Case_Updates","CaseID")` with the physical cache `=[Case_Updates_Cached]`, see `references/case-related-updates-vc-replacement-20260611.md`. For `Lookup[RowCount_Realtime]`, `RowCount[Count_RealTime]`, user-dependent count VCs, or HeartBeat cache-refresh throttling, use `references/appsheet-cached-count-performance.md`; for the 2026-06-11 HeartBeat case-count speedup example and analyzer follow-up, see `references/heartbeat-case-count-speedup-20260611.md`: keep global counts in `RowCount`, but cache user-dependent counts physically in `HR_E_A_S` / `HR_Employees_AppSheet_Settings` and refresh hourly/bounded batches rather than per sync. For HeartBeat runs taking ~120s or failing in `VerifyEventConditionAsync` / AppSheet cache-lock stack traces while scanning queue/repair slices, use `references/heartbeat-queue-polling-cache-locks.md`: identify event-condition polling bottlenecks and prefer physical queue-state flags/event-driven workers over repeated slice scans. When asked to prepare or apply a QueueState canary patch for a single lane such as `case_update_parent_sync`, use `references/queuestate-heartbeat-canary-dryrun.md` for the exact action/event/process-node shape, seed-row blocker check, stable-promotion caveat, and post-promotion runtime verification checklist. After any QueueState/HeartBeat canary, verify exportlogs by failure stack signature: replacing ready-slice scans with cross-table `LOOKUP()` may change `GetSliceDataFromCacheAsync`/`TopFunction` failures into `GetRootTableDataWithCachingAsync`/`SelectFunction` failures; if that happens, use `references/heartbeat-same-row-wake-flags.md` and move the wake-up bit onto physical columns on the touched `HeartBeat` row so the scheduled event condition is local-row-only while `QueueState` remains the durable source of truth. For low-urgency checker/repair lanes such as missing ActivityLog Session Items, that reference also covers using native hourly refresh + visible/manual repair action + clear-before-work so the lane does not repeatedly fire on every HeartBeat.
- For AppSheet user offboarding, departed-employee access audits, or questions about removing/dis-inviting users from the app, use `references/appsheet-user-access-offboarding.md`: check departed `HR_Employees` rows, canonical `HR_Employees_AppSheet_Settings`, top-level `/api/loadApp` exposure flags, and raw app JSON target occurrences; do not claim the live Users/share/allowlist pane is clear from `/api/loadApp` alone, and require separate approval before using authenticated editor-session inspection or making removals.
For `API_Target_Queue` vs `ProcessingQueue` cleanup/targetability questions, use `references/api-target-queue-maintenance.md`; preserve rows matching active ProcessingQueue work and prune only stale/duplicate/terminal-target rows after dry-run/readback. For duplicate `ProcessingQueue[QueueID]` keys or ambiguous AppSheet ref-action behavior on a Google Sheets-backed queue, use `references/processingqueue-duplicate-key-triage.md`: inspect the backing sheet directly, distinguish duplicate physical append payloads from true `UNIQUEID()` collisions, and quarantine duplicate losers safely.
- For AppSheet editor major-version saves, wrong-version recovery, or restore/version-history work, use `references/appsheet-editor-versioning-and-restore.md`: Pro-Design major versions are `YY.MMDD00` (for example `26.061800`), and AppSheet restore reverts content but does not rewind a mistakenly advanced monotonic version number.
- Security-filter performance/SQL-pushdown questions: use `references/security-filter-sql-pushdown.md`; do not call dynamic parent-table lists like `IN([ChildRef], Parent[Key])` strictly SQL-optimized even when they are a valid visibility fix.
- User-facing links: provide deployed-app links, not prototype links.
- Live writes/deletes/editor changes: dry-run/readback first and require confirmation unless the user has already explicitly asked for the exact safe bounded write. For AppSheet editor version changes, verify the Pro-Design `YY.MMDD00` version scheme before the first save; AppSheet restore creates a new latest version and cannot self-service roll back an accidental higher version lineage.
- AppSheet editor versioning: before manually setting `Version` or interpreting “major version”, use `references/appsheet-editor-versioning.md`. Pro-Design AppSheet major versions use the date-based `YY.MMDD00` convention (UTC), not semantic-major values such as `27.000001`; bad high versions can be difficult to undo because AppSheet enforces monotonic progression.
- Stable promotion: **always use `admin@prodesign-group.com` via the admin/tailscale-login browser profile first**. In this workspace the default/OpenClaw cookie can save `/api/saveapp` changes but may fail `Manage/SetStableVersion` with the misleading `This feature is only available as part of an Enterprise plan` error. Do **not** stop on that error until retrying with `/home/prodesign/.hermes/profiles/pdone/legacy-openclaw/workspace/browser-profiles/tailscale-login/Default/Cookies`. A `401` from that profile is a stale session, not the Enterprise-plan error: fall through to the cookie profile that can already `loadApp` before reporting promotion blocked. Promote with `POST https://www.appsheet.com/Manage/SetStableVersion`, form `appId=<app id>`, `version=<latest Version>`, `percentOnLatestVersion=0`, header `X-Requested-With: XMLHttpRequest`, then verify by fresh `/api/loadApp/<appId>` where `StableVersion == target` and by loading that stable version to confirm the target condition/object is present. For the reusable command shape and verification checklist, use `references/appsheet-stable-promotion-admin-profile.md`.
- For large AppSheet editor saves where `/api/saveapp` or `/api/loadApp` hangs while streaming the full app JSON, use `references/appsheet-editor-save-streaming-readback.md`: stream just enough live readback to verify target objects, treat later 409s as possible stale-payload/rebase signals, and prove the final business row state.
- For AppSheet performance patch tasks, do not stop at a saved/promoted version or a baseline scan if the stated goal includes patch + live test + documentation. Finish the full chain before reporting completion: definition readback, deployed API/business-state readback when applicable, post-promotion analyzer window split after the actual stable-promotion timestamp, sync/add/edit or workflow scans relevant to the bottleneck, wiki/runbook receipt update, and todo closure. If an early analyzer window straddles promotion, label it non-headline and run a clean post-cut window. For a concrete ActivityLog example where edit rows passed but sync/add stayed slow and nested analyzer timing selected `AL_SetFlag_ReadyToProcess` as the next bounded candidate, see `references/activitylog-inline-action-performance-20260613.md`.
- API edit/delete: verify the real key column from raw `/api/loadApp` metadata, not column order or guesses.
- Users cannot open the deployed app, or a bot says the event table and the process input must be the same: load `references/appsheet-editor-api-saveapp-pitfalls.md` before treating `IsValid` as proof the app launches. Severity-0 automation errors set `IsRunnable` false. A non-runnable stable version blocks every user when percent-on-latest is 0, even if the editor still opens.
- Automation/debugging: separate definition truth (wired?) from runtime truth (did it run?) and verify final business state, not just queue/job existence.
- AppSheet functions/expressions: check the official function list before asserting non-trivial syntax or availability.
