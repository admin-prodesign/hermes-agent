# Automation reliability — non-negotiables

## Non-Negotiables
- Automations must be idempotent or explicitly guarded against duplicate side effects.
- Stateful workflow/outbox jobs must preserve `verification_pending` until external side effects are reconciled; invalidation, edit/revision, mismatch, lease expiry, and operator-failure paths must not silently turn ambiguous sends into retryable failures. Only a definitely-unsent operation may enter a retryable failed state.
- In evidence-driven approval workflows, the durable observation path must be the only way to create counted approvals: persist the source post first, count evidence and approval atomically, make terminal non-counted posts non-replayable, and back workflow ownership with composite relational constraints.
- Treat Office/artifact qualification as a live cryptographic check, not a cached manifest boolean. Re-verify the signed receipt and exact artifact/template hash at every production verification/compile boundary; leave the production trust store empty and fail closed until an approved public key is installed.
- Before creating a recurring job from a Mattermost/thread request, check for an existing active job with the same purpose/delivery context; if one exists, update/report the existing receipt/job ID instead of creating another.
- When a user asks to redirect an existing recurring agent/report “to this thread/channel in the future” or to change its delivery formatting, update the matched job’s `deliver` target and self-contained prompt/formatting instructions in place; then read back the job receipt (`deliver`, `enabled/state`, `next_run_at`, `last_status`, `last_delivery_error`) before reporting success. For Telegram rich-formatting requests, explicitly tell the job to use Telegram-compatible Markdown (headings, bold labels, bullets, inline code, short tables where helpful) while keeping reports concise.
- When a user says “stop reminder/monitor/job …”, or says a generator can be parked because its source feed stopped, treat stopping the existing automation as the first deliverable even if the same message asks for a replacement workflow. Disable/pause the exact matched job, record a human-readable paused/stopped reason with requester/thread context, clear `next_run_at` where applicable, then read back and report the job ID plus before/after enabled/state/next-run receipt before continuing. If the script can overwrite an external document, pausing the scheduler is not enough: make the script and its wrapper exit before that write, and remove supervisor safe-repairs that rerun the write. A PD One session's bare `hermes cron` does not see default-profile jobs. Use `hermes -p default` for the default cron registry.
- Every unattended path needs visible failure handling: logs, receipts, retry state, and an alert path when appropriate.
- Hermes cron failure cards truncate script stdout. Read the job `last_error` and the script state file before you name the cause. The card text is not the full receipt.
- For a PD One LINE webhook tunnel-guard failure, load the pd-one-admin LINE webhook operations note and follow Tunnel-guard alert triage. Do not treat `pip install aiohttp` as the cause until the live release venv import fails.
- For script-only/no-agent cron jobs, do not assume `deliver=origin` or a visible cron failure message means the failure was federated to PD One/admin triage. Verify federation separately by checking the configured bridge/queue/failed-event store and supervisor remediation plans. If the job only posts cron failures to the origin thread, classify that as a missing guarded-triage bridge and either add/approve a guarded wrapper or clearly report that federation did not happen.
- Before writing a new remediation plan, search existing remediation-plan files for the same automation plus the same gap/state class. If an exact match already exists, do not duplicate it; report the existing plan path as the backlog receipt and only write a new plan when the gap is genuinely distinct.
- Keep recurring scanner/poller critical paths bounded: capture raw evidence first, and move expensive model/agent enrichment (translation, summarization, quality scoring) to a separate/backfill path or disable it in the cron/systemd run when it can spawn per-row work and exceed the wrapper timeout.
- Use dry-run/smoke-test loops before live sends or writebacks; verify actual delivery/write receipts.
- After writing or changing any unattended script/job, double-check executable paths under the same environment the automation will use (cron/systemd/non-login shell). Prefer absolute paths for non-system CLIs, set a bounded PATH explicitly, and run a cron/systemd-equivalent smoke test so path issues do not fail silently.
- Do not call bare `python3` from a cron child. Hermes cron runs a `.py` job with `sys.executable`, but a child `python3` uses PATH and hits the standalone tools interpreter, which does not carry the release venv's third-party modules. Pin the child to `/home/prodesign/.hermes/releases/current/.venv/bin/python3`, not a hash-specific release path and not `sys.executable` of a parent that a wrapper started with `/usr/bin/python3`. A shebang is not a call site: cron ignores it. When asked to fix every job with the same import failure, scan enabled jobs' `last_error`, follow wrappers to the bare `python3` child, and skip shells that already set `PATH` to `/usr/bin` before calling `python3`. Do not retarget those shells, and do not widen the fix to a different missing module. Prove the pinned interpreter can import the child before editing. Verify a write-capable sync with `--help` or its dry-run flag, not `--execute`. For a quiet reaper, run it once, then read the next scheduled tick: `last_status=ok`, failure streak 0, and empty stdout is the healthy receipt. Do not pip-install into the standalone tools interpreter.
- Hermes no-agent cron `script` values must be regular files inside the ticking profile's `scripts/` directory. A relative name that is a symlink into another profile or `~/.hermes/scripts/` fails with `Blocked: script path resolves outside the scripts directory` because `Path.resolve()` follows the symlink. Copy the worker into the profile scripts dir (or wrap it with a regular in-profile `.sh`); do not symlink across profiles. Employee-facing `deliver` jobs should set `failure_deliver=local` (or Admin) so resolver/engine errors stay off the operational channel.
- A habit monitor for a newly required record must name a visible proxy event and state what that proxy cannot see. Do not treat a count of the new records as compliance, and do not message the staff group unless the requester asks for that follow-up. Time-box the window and stay silent after it ends.
- Do not promise future follow-up unless a real cron/job/watchdog exists.
- For critical one-shot delayed reports, do not stop at `cronjob.create` receipt alone. Prefer a deterministic script/no-agent job when possible; otherwise include a self-contained prompt, explicit `deliver='origin'`, evidence paths, and a recovery instruction. After creation, read back the job and, when the user later asks why a report did not arrive, check for the specific job ID in cron/session receipts before assuming a delivery failure. If the due job did not run, run the report immediately and disclose the missed-fire plainly.
- For no-agent cron watchdogs/sync jobs, design stdout deliberately: empty stdout for normal no-op ticks, concise human-readable Markdown for chat-visible edits/alerts/errors, and a local JSON/log receipt for audit. Avoid raw JSON in notifications to Andy unless explicitly requested; keep `--json` paths for machine-to-machine checks.
- When redirecting a no-agent cron's human-visible output to email, wrap the existing script/guarded wrapper rather than rewriting business logic; set cron `deliver=local` to prevent duplicate chat posts; verify via email-helper dry-run and cron readback before reporting completion.
- For recurring registry briefings with many tracked items, do not emit an ungrouped wall of project bullets. Include a grouping field such as primary channel/business area, normalize lifecycle statuses (Active/Review/Paused/Retire), and let low-value rows opt out of the briefing while remaining in the canonical registry.
- Route recurring automation failures to the owner/admin alert lane by default, not the originating implementation/troubleshooting thread, unless the user explicitly wants thread-local delivery. For PD One Mattermost operational jobs, prefer the PD One Admin channel (`5gmqtwqf7bde3cyihas79xi8ie`) for failure/stale-state alerts, and verify both the cron `deliver`/`origin` route and the supervisor registry `alert_expectation` after edits.
- Protect primary alerts; fallbacks should add resilience, not spam.
- Treat Google/gog `i/o timeout`, `Client.Timeout exceeded while awaiting headers`, and `context deadline exceeded` as transient OAuth/network failures. Retry the read and suppress Admin notify until they persist. Do not require the exact phrases `timed out` or `timeout awaiting response headers`; keep those markers in both `sheets_safe_ops.py` and `transient_failure_gate.py`. Project List source-key watchdog (`4d7c09917fd9`) applies that gate in-script: retry once, then 3 / 1800s quiet suppress; persistent transients use a designed Admin line instead of a Hermes engine traceback card.
- Harmless no-op pollers (Town Square PPT GitHub `releases/latest`) must not page Admin on `dial tcp`/`i/o timeout`. Use `transient_failure_gate.py --suppress-transient` so those ticks exit 0 with empty stdout; non-transient failures still pass stdout/rc.
- Employee-facing `deliver=origin` jobs must not post the first transient failure into the origin thread. Use a gated wrapper that exits 0 while the failure is still transient, and set `failure_deliver=local` so Hermes engine error cards stay off the employee thread. Daily jobs need a multi-day gate window (SDS/Facilities: threshold 2 / 3 days), not 3-in-30-minutes. `pd_one_supervisor_apply_wrappers.py` must choose that daily gate from the job schedule (`0 1 * * *` and other single hour+minute cron tokens); do not stamp 3/1800 on a daily wrap.
- PD Neo daily non-critical digest (`870dd7349151` / `pd_neo_daily_noncritical_digest_send.sh`) is local-only. Do not re-add `--send` or `pd_neo_notify.py` Discord delivery unless Andy explicitly asks. Dated `YYYY-MM-DD.md` files keep a 90-day Taipei retention window; do not delete `latest.*` or `summary-cache.json`.
- Repeating chat reminders must delete the previous bot reminder in the same thread unless a non-bot reply landed after it. Match the exact bot, channel, root, and reminder marker; never delete the root or a failure card as a reminder.
- The live daily briefing refresh must pass `--allow-previous-day-schedule-context` to the incident summarizer. The production-schedule source timestamp stays on the previous calendar day until the morning publish; treating that as a hard failure marks the 5-minute oneshot failed all night and makes autofix ask for a useless restart. The morning briefing runner must keep the strict same-day gate.
- Self-heal must not page or offer a restart for a timer-triggered oneshot that has been failed for under 20 minutes. When a oneshot stays failed, include the journal error line and say the timer already retries.
